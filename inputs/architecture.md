# Архитектура микросервиса ИИ-проверки ЭНД и план реализации

Oct 5, 2026 · @Amadeus M

## 1. Ключевые решения

Фронт не обращается к микросервису напрямую: он отправляет черновик раздела 2 в HSE backend, тот сохраняет снимок, обезличивает его и сам вызывает микросервис по внутренней сети. Так проверка всегда идёт по данным, которые сервер считает подлинными, а ключи LLM и правила недоступны из браузера.

| № | Решение | Почему |
| --- | --- | --- |
| 1 | Фронт → только HSE backend (BFF). Микросервис без публичного входа | Фронту нельзя доверять: запрос из браузера можно подделать; права на ЭНД проверяет только HSE |
| 2 | Проверяется **снимок**, сохранённый HSE backend, а не JSON «как пришёл» | Шлюз отправки сравнивает хеш снимка с хешем проверенного; подмена после проверки невозможна |
| 3 | Организация, подразделение, категория, роль — из БД HSE, не из запроса фронта | Нельзя проверить чужой ЭНД или подменить категорию, чтобы обойти правила |
| 4 | В микросервис уходят коды, ID справочников и тексты мероприятий; ФИО, ИИН, телефоны — нет | Персональные данные не покидают HSE и не попадают в LLM |
| 5 | Микросервис держит свою копию справочников и правил, синхронизируемую по версии | Нет прямого доступа к БД HSE; проверка воспроизводима по версии |
| 6 | Ответ в два шага: находки кода сразу (≤ 1 с), находки LLM — следом (≤ 10 с) | Пользователь видит результат сразу; LLM не задерживает основное |
| 7 | Шлюз «Отправить на утверждение» проверяет HSE backend | Решение о допуске принимает владелец ЭНД, а не внешний сервис |
| 8 | Микросервис — источник истины по прогонам, находкам и действиям; HSE хранит ссылку `aiRunId` на ЭНД | Единый неизменяемый журнал проверки |

## 2. Компоненты и зоны ответственности

Система состоит из трёх звеньев: фронт ЭНД, HSE backend и микросервис проверки; браузер видит только HSE backend, микросервис и LLM-шлюз доступны только изнутри.

&#91;embedded content: компоненты · кто кого вызывает\]

HSE backend — единственная точка входа и владелец решения о допуске; микросервис только проверяет и рекомендует. Исходящий трафик микросервиса разрешён только на LLM-шлюз.

## 3. Потоки взаимодействия

Проверка идёт в два шага: HSE backend получает находки кода в ответе на запуск, а находки LLM — обратным вызовом; фронт забирает итог опросом или SSE.

&#91;embedded content: основная проверка · 14 сообщений\]

Если callback не пришёл за 15 с, HSE backend сам запрашивает `GET /v1/checks/{runId}`.

**Ответ на вопрос-фактор**

1. Пользователь отвечает «Да / Нет» → фронт: `POST …/ai-checks/{runId}/answers`.
2. HSE backend сохраняет ответ в черновике (фактор входит в `contentHash`) и вызывает `POST /v1/checks/{runId}/answers`.
3. Микросервис создаёт новый прогон; неизменённые строки берутся из кеша, ответ обычно ≤ 2 с.

**Действие по находке**

1. Фронт: `POST …/ai-findings/{findingId}/actions`.
2. HSE backend проверяет права, добавляет `userRef` и время, передаёт в `POST /v1/findings/{findingId}/actions`.
3. При `accept` фронт подставляет текст, сохраняет черновик и через 1,5 с запускает повторную проверку.

**Отправка на утверждение**

1. Фронт: существующий вызов отправки ЭНД.
2. HSE backend считает `contentHash` текущего состояния и вызывает `GET /v1/gate?endRef=…&contentHash=…`.
3. Вердикт `allowed = false` → 409 с перечнем `blockers`; `true` → ЭНД уходит на утверждение, `aiRunId` сохраняется в ЭНД.

## 4. Контракт фронт ↔ HSE backend

Фронт передаёт только содержимое раздела 2, которое ввёл пользователь, и ответы на вопросы; всё остальное (организация, категория, описание, даты, флаги, роли) HSE backend берёт из своей БД. Обратно фронт получает готовые к показу находки и состояние шлюза.

**Эндпоинты HSE backend для фронта**

| Метод | Путь | Назначение |
| --- | --- | --- |
| PUT | `/api/end/{endId}/section2` | Сохранить черновик раздела 2 (заголовок `If-Match: <etag>`). Ответ: `{draftVersion, etag}` |
| POST | `/api/end/{endId}/ai-checks` | Запустить проверку сохранённого черновика. Тело: `{draftVersion, mode: "full" \| "additions"}` |
| GET | `/api/end/{endId}/ai-checks/{runId}` | Результат прогона (опрос раз в 1 с до `status = done`) или SSE `/events` |
| POST | `/api/end/{endId}/ai-checks/{runId}/answers` | Ответы на вопросы-факторы: `{answers: {F02: "yes"}}` → повторная проверка |
| POST | `/api/end/{endId}/ai-findings/{findingId}/actions` | Принять / изменить / отклонить находку |
| GET | `/api/end/{endId}/ai-checks?limit=20` | История проверок (вкладка «История ИИ-проверки») |
| GET | `/api/end/{endId}/submit-gate` | Можно ли отправить на утверждение и что мешает |

**Что фронт передаёт в черновике раздела 2**

```json
{
  "locale": "ru",
  "measures": [
    {
      "rowId": "7f1c…",
      "section": "5.3",
      "text": "При работе вблизи ЛЭП установить на грузоподъёмный механизм…",
      "catalogItemId": 1042,
      "catalogItemVersion": 3,
      "origin": "catalog",
      "notApplicable": false,
      "notApplicableReason": null
    }
  ],
  "risks": [
    {
      "rowId": "a91e…",
      "hazardId": 311,
      "victimIds": [12],
      "harmIds": [45, 46],
      "existingControlIds": [801],
      "b1": 2, "p1": 3,
      "additionalControlIds": [915],
      "b2": 1, "p2": 2,
      "controlResponsibleRoleId": 4,
      "implementWhenId": 1
    }
  ],
  "factorAnswers": {"F02": "unknown", "F05": "no"}
}
```

Правила для полей:

- `rowId` — UUID, создаётся фронтом один раз для строки и не меняется; на него ссылаются находки.
- `origin`: `catalog` — выбрано из справочника и не изменено; `catalog_edited` — выбрано и изменено; `manual` — введено вручную. Фронт выставляет по факту действия пользователя; HSE backend перепроверяет сравнением с текстом записи справочника.
- `notApplicable = true` — пункт помечен «Не требуется» (прочерк); `notApplicableReason` — обоснование для условных пунктов.
- Р в рисках фронт **не передаёт**: его считает сервер.
- Фронт **не передаёт**: `orgId`, `unitId`, категорию, описание работ, даты, флаги раздела 2, `userId`, роли, ФИО — всё это HSE backend берёт из ЭНД и сессии.

Ограничения на входе (проверяет HSE backend, при нарушении — 422 с полем): текст мероприятия ≤ 2000 символов, ≤ 30 строк на пункт, ≤ 50 строк рисков, тело запроса ≤ 256 КБ, В и П — целые 1–5, все ID существуют в справочнике и активны.

**Что фронт получает**

{

  "status": "llm_pending",
  "contentHash": "sha256:9b1…",
  "rulesetVersion": "omg-1.1.0",
  "summary": {"critical": 4, "significant": 2, "recommendation": 1, "questions": 1, "autofix": 1},
  "findings": [
    {
      "findingId": "f_8c2…",
      "ruleCode": "S02",
      "severity": "critical",
      "kind": "issue",
      "source": "rules",
      "target": {"type": "measure", "section": "5.2", "rowId": "c40d…"},
      "title": "Тестовое значение",
      "message": "В пункте 5.2 указано тестовое значение «Тест».",
      "evidence": "Тест",
      "recommendation": {"mode": "replace", "text": "…", "catalogItemIds": [1017]},
      "basis": {"doc": "Правила № 344", "clause": "заполнение граф", "url": "https://adilet.zan.kz/rus/docs/V2000021151"},
      "allowedActions": ["accept", "edit", "reject"],
      "state": "open"
    }
  ],
  "questions": [{"factorCode": "F02", "text": "Есть ли ВЛ ближе 30 м от крана?", "options": ["yes", "no"]}],
  "gate": {"allowed": false, "blockers": [{"code": "critical_open", "text": "4 критичных замечания не обработаны"}]}

```

`recommendation.mode`: `replace` — заменить текст строки; `append` — добавить новую строку в пункт; `set_field` — изменить поле строки рисков (`field`, `value`); `select_ids` — выбрать значения справочника. Тексты `title`, `message`, `recommendation.text` приходят на языке `locale`; фронт их не собирает сам.

Действие по находке: `{"action": "accept" | "edit" | "reject", "reasonCode": "not_applicable" | "done_otherwise" | "ai_error" | "other", "comment": "…", "appliedText": "…"}`. `reasonCode` обязателен для `reject`.

## 5. Контракт HSE backend ↔ микросервис

HSE backend отправляет микросервису обезличенный снимок раздела 2 с контекстом из БД; микросервис синхронно возвращает находки кода, а находки LLM доставляет обратным вызовом (callback) в HSE backend с подписью.

**API микросервиса (только внутренняя сеть, префикс `/v1`)**

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/v1/checks` | Запуск прогона. Заголовки: `Authorization: Bearer <сервисный JWT>`, `Idempotency-Key: <contentHash>`, `X-Request-Id`. Ответ 200 — находки кода, статус LLM |
| GET | `/v1/checks/{runId}` | Полный результат прогона (резерв, если callback не дошёл) |
| POST | `/v1/checks/{runId}/answers` | Ответы на вопросы-факторы → новый прогон с тем же снимком |
| POST | `/v1/findings/{findingId}/actions` | Запись действия пользователя в журнал |
| GET | `/v1/gate?endRef=…&contentHash=…` | Вердикт для шлюза: есть ли актуальный прогон и необработанные критичные |
| GET | `/v1/health`, `/v1/ready` | Проверки живости и готовности |

**Callback в HSE backend:** `POST /internal/ai-check/callback` с телом `{runId, endRef, status, findings[], questions[]}` и заголовками `X-Signature: sha256=<HMAC тела>`, `X-Timestamp`. HSE отклоняет запрос старше 5 минут или с неверной подписью, затем пересылает находки фронту.

- `endRef`, `userRef` — непрозрачные идентификаторы (HMAC от внутреннего ID с секретом HSE); по ним нельзя восстановить человека без HSE.
- Время — ISO 8601 со смещением `+05:00` (единый часовой пояс РК).
- `catalogVersion` — версия справочников, с которой работал пользователь. Если у микросервиса такой версии нет — ответ 409 `catalog_version_unknown`, микросервис запускает синхронизацию, HSE повторяет запрос через 1 с.

```

**Коды ошибок микросервиса**

| Код | Когда | Действие HSE backend |
| --- | --- | --- |
| 400 `schema_invalid` | Тело не проходит JSON Schema | Ошибка разработки: лог, сообщение «Проверка временно недоступна» |
| 401 / 403 | Неверный или просроченный сервисный токен | Обновить токен, повторить один раз |
| 409 `catalog_version_unknown` | Нет версии справочников | Повтор через 1 с, максимум 3 раза |
| 409 `run_exists` | Тот же `Idempotency-Key` | Вернуть существующий `runId` |
| 422 `business_invalid` | Несуществующие ID справочников, неизвестная категория | Показать ошибку данных |
| 429 | Превышен лимит | Повтор после `Retry-After` |
| 503 | Сервис недоступен | Баннер «Проверка недоступна»; шлюз работает по правилу из раздела 10 |

## 6. Безопасность

Главные угрозы — подмена данных из браузера, обход шлюза отправки, утечка персональных данных в LLM и внедрение инструкций в текст мероприятий; каждая закрывается на стороне сервера, а не фронта.

| Угроза | Мера | Где |
| --- | --- | --- |
| Запрос к чужому ЭНД или подмена категории/организации | Права на ЭНД проверяются по сессии; контекст берётся из БД, не из тела запроса | HSE backend |
| Отправка на утверждение без проверки или с изменениями после неё | Шлюз сравнивает `contentHash` текущего снимка с хешем проверенного; проверка только на сервере | HSE backend |
| Прямой доступ к микросервису | Нет публичного ingress; NetworkPolicy пускает только HSE backend; mTLS внутри кластера | Инфраструктура |
| Поддельный вызов микросервиса | Сервисный JWT (client credentials, `aud = ai-check`, срок 5 мин), проверка `iss` и подписи | Микросервис |
| Поддельный callback | HMAC-SHA256 тела + `X-Timestamp`, окно 5 мин, сравнение в постоянное время | HSE backend |
| Персональные данные в LLM | Белый список полей запроса; маскирование: ФИО участников ЭНД → `[РОЛЬ]`, ИИН (12 цифр) → `[ИИН]`, телефоны `+7…` → `[ТЕЛ]`, e-mail → `[EMAIL]`; `endRef` и `userRef` непрозрачны | HSE backend |
| Внедрение инструкций в текст мероприятия («игнорируй правила…») | Текст пользователя передаётся в LLM как данные в ограничителях; системный промпт запрещает выполнять инструкции из данных; ответ — только по JSON Schema; критичность ставит код, а не LLM; верификатор отбрасывает находки без кода правила | Микросервис |
| Перегрузка и злоупотребление | Лимиты: тот же `contentHash` — возврат готового прогона; не более 1 нового прогона на ЭНД за 5 с и 60 на пользователя в час; лимит размера тела 256 КБ | HSE backend + микросервис |
| Вредоносный текст (HTML, скрипты) в находках | Фронт показывает тексты только как текст (без `innerHTML`); микросервис удаляет теги на входе | Фронт + микросервис |
| Утечка ключей LLM | Ключи только в хранилище секретов микросервиса; исходящий трафик разрешён только на адрес LLM-шлюза | Микросервис, инфраструктура |
| Изменение журнала проверок | Таблицы прогонов, находок и действий — только вставка; права UPDATE/DELETE у роли приложения отозваны | БД микросервиса |
| Перехват трафика | TLS 1.2+ везде, включая внутренние вызовы (mTLS) | Инфраструктура |

Маскирование выполняется до отправки в микросервис, а не только перед LLM: тогда персональные данные не попадают и в журнал микросервиса. Список ФИО для маскирования HSE берёт из участников этого ЭНД (производитель, допускающий, ответственный руководитель, бригада).

## 7. Внутренняя архитектура микросервиса

Микросервис делится на синхронную часть (API, оркестратор, движок правил) и асинхронную (LLM-воркеры, верификатор, callback); падение LLM не задевает первую.

&#91;embedded content: модули микросервиса · 9 частей\]

Таблицы БД — как в ТЗ (раздел 3): `ai_ruleset`, `ai_rule`, `ai_matrix`, `ai_factor`, `ai_org_param`, `ai_check_run`, `ai_finding`, `ai_finding_action`, `ai_llm_cache`, плюс `catalog_snapshot` (версии справочников) и `callback_outbox`.

| Слой | Рекомендация | Почему |
| --- | --- | --- |
| Язык и фреймворк | Python 3.12 + FastAPI, Pydantic v2 | Работа с текстом, regex, LLM-клиенты; схемы из Pydantic → OpenAPI и JSON Schema |
| Морфология | Стемминг по основам из словаря маркеров; для RU — pymorphy3 | Маркеры в каталоге заданы основами слов |
| Сходство текстов | Нормализация + хеш для точного совпадения; rapidfuzz для «изменено» (≥ 0,85) | Быстро, без внешних сервисов |
| БД | PostgreSQL 16, отдельная схема | Журнал только вставка, jsonb для параметров |
| Кеш и лимиты | Redis | Пакет правил, справочники, кеш LLM, счётчики лимитов |
| Очередь | Та, что уже есть в HSE (RabbitMQ / Redis Streams) | Одна инфраструктура на поддержке |
| Наблюдаемость | OpenTelemetry, Prometheus | Единый трейс HSE → сервис → LLM |

Если команда HSE пишет на другом стеке (Java, .NET, Go), движок правил переносим: правила и regex живут в данных (`omg_ai_check_rules.json`), а не в коде.

## 8. Синхронизация справочников и правил

Справочники остаются в HSE и редактируются там; микросервис забирает их версиями через экспорт HSE и хранит у себя. Правила проверки, наоборот, живут в микросервисе и не требуют выпуска HSE.

| Что | Владелец | Как попадает в микросервис |
| --- | --- | --- |
| Справочники мероприятий, опасностей, «кто», «как», мер контроля, ролей, сроков внедрения | HSE | Экспорт `GET /internal/catalog/export?since=<version>` + событие `catalog.updated` |
| Разметка справочников (тип записи, пункт 5.x, факторы, ключевые элементы, иерархия мер, «влияет на», связи) | HSE (поля в тех же справочниках) | В том же экспорте |
| Профили подразделений (объекты, факторы по умолчанию) | HSE | В том же экспорте |
| Правила S, N, матрица, правила категорий, RA, параметры, словари маркеров, промпты | Микросервис | Админка микросервиса, импорт `omg_ai_check_rules.json` |

Порядок синхронизации справочников:

1. При изменении справочника HSE увеличивает `catalogVersion` (монотонная строка: `omg-cat-2026.10.01-3`) и публикует событие `catalog.updated {orgCode, version}` в шину (или вызывает `POST /v1/sync` микросервиса).
2. Микросервис запрашивает `GET /internal/catalog/export?since=<своя версия>` и получает изменения: добавленные, изменённые и деактивированные записи с их версиями.
3. Микросервис сохраняет новую версию целиком (старые версии хранятся, чтобы перепроверить старые ЭНД), прогревает кеш, отвечает `200` на `GET /v1/catalog/version`.
4. Если пришёл запрос с неизвестной `catalogVersion` — 409 и внеплановая синхронизация (раздел 5).
5. Резерв: опрос версии раз в 10 минут, если событие потерялось.

Записи справочника не удаляются, а деактивируются: ЭНД, созданные раньше, ссылаются на старые ID.

Версия правил (`rulesetVersion`) меняется только через черновик → прогон на эталонном наборе → утверждение HSE-экспертом → активацию. В каждом прогоне записаны обе версии: `catalogVersion` и `rulesetVersion`.

## 9. Изменения на фронте и в форме ЭНД

Фронт отвечает за удобный ввод и показ, но ничего не решает сам: проверки на клиенте — только подсказки, всё повторяется на сервере.

| Что | Сейчас | Нужно |
| --- | --- | --- |
| Кнопка «Проверить с ИИ» | Недоступна, пока не заполнены все поля рисков | Доступна всегда; незаполненные строки рисков ИИ сам возвращает как находку RA02. Раздел 5 проверяется независимо от рисков |
| Выбор из справочника | Подставляется только текст | Хранить `catalogItemId`, `catalogItemVersion`, `origin`; при правке текста после выбора `origin` → `catalog_edited` |
| Прочерк | Пользователи пишут «тест» | Кнопка «Не требуется» у каждого пункта; для условных пунктов — поле обоснования |
| Условия производства работ | Нет | Блок вопросов-факторов над п. 5.1 (до 8–10 на категорию), значения по умолчанию из профиля |
| Р в таблице рисков | — | Только чтение, считается автоматически |
| «Кто будет контролировать» и «Когда внедрить» | Есть в таблице | Обязательны, если заполнены доп. меры (новые правила RA24, RA25 — ниже) |
| Подсветка | Красная рамка для критичных | Привязка по `rowId` и `section`; цвета по критичности; клик → карточка в панели «Замечания» |
| Карточка находки | Принять / Редактировать / Отклонить | То же + основание (документ и пункт), отметка «сгенерировано ИИ», обязательная причина при отклонении |
| После «Принять» | — | Текст подставляется в строку, черновик сохраняется, повторная проверка запускается автоматически через 1,5 с после последнего изменения; неизменённые строки берутся из кеша |
| Результат | Панель справа | Сначала находки кода, затем находки ИИ по мере готовности; при `llm = unavailable` — баннер |
| Устаревший результат | — | Если пользователь изменил раздел 2 после проверки — пометка «Результат устарел», шлюз закрыт до новой проверки |
| «Отправить дополнения» | Есть | Режим `mode = additions`: проверяются только добавленные строки и их связь с уже согласованными |
| Безопасный вывод | — | Тексты находок выводятся только как текст, без `innerHTML` и без разметки |

Новые правила для столбцов таблицы рисков, которых не было в каталоге:

- **RA24** (существенно): заполнены доп. меры, а «Кто будет контролировать» или «Когда внедрить» пусты.
- **RA25** (критично): «Когда внедрить» позже начала работ для доп. меры, без которой исходный риск в недопустимой зоне. Такая мера должна быть выполнена до допуска.

Порядок вызовов на фронте при нажатии «Проверить с ИИ»: сохранить черновик (`PUT …/section2`) → получить `draftVersion` → `POST …/ai-checks` → показать находки кода из ответа → опрашивать `GET …/ai-checks/{runId}` раз в 1 с (или слушать SSE) до `status = done`, не дольше 20 с.

Состояния, события и крайние случаи интерфейса: Взаимодействие интерфейса; экраны — в [мокапе](https://claude.ai/artifact/9qupfoqZPGAynuRTRWpYpr).

## 10. Эксплуатация

Микросервис разворачивается в том же кластере, что и HSE, в 2+ экземплярах с отдельной БД; целевые показатели — 99,5% доступности в рабочее время, находки кода за 1 с и полный результат за 10 с (p95).

| Параметр | Значение |
| --- | --- |
| Среды | dev → test (с копией обезличенных ЭНД) → prod; эталонный набор прогоняется на test перед каждой выкладкой правил или кода |
| Развёртывание | Контейнеры, 2+ реплики API и 2+ воркера LLM; выкладка без простоя (rolling) |
| Хранилища | PostgreSQL (схема микросервиса), Redis (кеш справочников, кеш LLM, лимиты), очередь задач (Redis Streams или RabbitMQ — что уже есть у HSE) |
| SLO доступности | 99,5% запросов `POST /v1/checks` без ошибки 5xx в рабочие часы |
| SLO времени | Находки кода ≤ 1 с (p95); полный прогон ≤ 10 с (p95); таймаут LLM 12 с |
| Метрики | Длительность этапов, доля таймаутов и невалидных ответов LLM, попадания в кеш, число находок по правилам, доля принятых и отклонённых находок по правилам, расход токенов |
| Логи | Структурированные, с `X-Request-Id` и `runId`; без текстов мероприятий в логах уровня INFO |
| Трассировка | OpenTelemetry: HSE backend → микросервис → LLM-шлюз одним трейсом |
| Оповещения | Ошибки 5xx > 2% за 5 мин; p95 > 10 с за 15 мин; доля таймаутов LLM > 10%; рассинхрон `catalogVersion` > 30 мин |
| Хранение | Прогоны, находки, действия — не меньше 1 года после закрытия ЭНД (как сам ЭНД по Правилам № 344); резервное копирование ежедневно |

Шлюз отправки при недоступности сервиса:

1. Микросервис ответил, LLM недоступен — шлюз работает по находкам кода; это штатный режим.
2. Микросервис недоступен полностью — отправка блокируется с сообщением «Проверка ИИ недоступна». Ответственный руководитель или администратор может отправить ЭНД с отметкой «без ИИ-проверки» и обязательной причиной; событие пишется в журнал HSE и попадает в ежедневный отчёт.

## 11. План реализации

Работа занимает 7 двухнедельных спринтов: контракты утверждаются в первом, проверки кодом работают на test после третьего, пилот в ОМГ — в шестом и седьмом.

Условия контрольных точек:

1. **Контракты утверждены** (конец С1): OpenAPI фронт ↔ HSE и HSE ↔ микросервис подписаны тремя командами; выбрано размещение LLM.
2. **Код-проверки на test** (конец С3): S, N, матрица и RA работают сквозь фронт → HSE → сервис; справочники ГПР и высоты размечены.
3. **Полный воркфлоу** (конец С5): LLM, верификатор, callback, шлюз отправки; тест-кейсы 1–18 из ТЗ проходят.
4. **Приёмка** (конец С7): метрики ТЗ на эталонном наборе ОМГ, 2 недели пилота с блокировкой без инцидентов доступности.

Разметка справочников — критический путь: без неё к концу С3 движок правил нечего тестировать на реальных данных.

## 12. Риски проекта и открытые вопросы

Главный риск — не техника, а данные: без разметки справочников и утверждённых правил проверка будет либо шумной, либо пустой.

| Риск | Последствие | Что делаем |
| --- | --- | --- |
| Справочники не размечены к старту | Правила применимости и рисков не работают, всё уходит в LLM | Разметка ГПР и высоты — до спринта 3; остальные категории — параллельно с разработкой |
| Много ложных замечаний | Пользователи отклоняют всё не читая | Пилот в режиме «только предупреждения» на 2 недели; правила с точностью < 75% понижаются до рекомендаций |
| Требования к размещению данных запрещают внешний LLM | Нужна локальная модель, другие сроки и железо | Решить до спринта 2; LLM-адаптер изолирован, модель меняется без правок движка |
| Фронт не передаёт `origin` и `catalogItemId` | Нельзя отличить выбор из справочника от ручного ввода, лишняя нагрузка на LLM | HSE backend дополнительно сопоставляет текст со справочником; поля фронта — обязательны в контракте |
| Тексты ЭНД содержат ФИО и другие персональные данные | Нарушение требований к ПДн | Маскирование в HSE до отправки, тесты на маскирование в приёмке |
| Основания «сверить» не подтверждены | Критичность без нормативной опоры | Такие правила активны максимум как «существенные» до подтверждения HSE-экспертом |

Открытые вопросы:

- [ ] Где размещается LLM (облако или собственный контур) и кто согласует
- [ ] Есть ли в HSE шина событий; если нет — синхронизация опросом и `POST /v1/sync`
- [ ] Кто в HSE выдаёт сервисные токены (существующий IdP или отдельный)
- [ ] Нужен ли режим отправки «без ИИ-проверки» и для каких ролей
- [ ] Шкалы и зоны риска ОМГ для RA10, RA11, RA21, RA25
- [ ] Казахские тексты сообщений и рекомендаций: кто переводит и утверждает
