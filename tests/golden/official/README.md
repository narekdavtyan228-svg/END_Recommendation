# Эталонные кейсы 0–18

Каждый файл `case_NN.json`:

- `request` — тело `POST /v1/checks` (схема из документа архитектуры, раздел 5). `end.contentHash = null` — тест считает его по `aicheck/hashing.py`.
- `mode`: `code_only` — проверяется результат кодового этапа (заглушка LLM возвращает пустой список находок); `integration` — через API с БД и заглушкой LLM.
- `llm_scenario` — сценарий заглушки (`ok`, `timeout`).
- `expect.must_include` — находки, которые обязаны быть (сравнение по `rule_code`, `severity` и полям `target`, которые указаны; не указанные поля не сравниваются).
- `expect.must_include_any` — список групп: из каждой группы должна быть хотя бы одна находка.
- `expect.must_not_include` — коды правил, которых быть не должно.
- `expect.must_not_include_severity` — уровни, которых не должно быть ни у одной находки.
- `expect.questions` — коды факторов, по которым должен прийти вопрос.
- `expect.must_not_mention` — подстроки, которых не должно быть в текстах находок.
- Кейсы 16–18 описаны шагами `steps`.

Справочник для кейсов — `fixtures/test_catalog.json` (версия `test-cat-1`). Для тестов параметр P15 переопределяется: `implement_before_start_ids = [1]`.

Кейс 0 — контроль базы: на нём не должно быть критичных и существенных замечаний. Если они есть, сначала исправить правило или базу, потом смотреть остальные кейсы. Расхождения записывать в DECISIONS.md.
