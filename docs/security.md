# Информационная безопасность: описание для ТД ИБ

Документ описывает, как сервис ИИ-проверки раздела 2 ЭНД закрывает требования Единых требований в области ИКТ и ИБ
(постановление Правительства РК № 832), Закона «О персональных данных и их защите» № 94-V и Закона «Об искусственном
интеллекте» № 230-VIII. Применимость и класс системы подтверждает служба ИБ ОМГ; каждое требование ниже закрыто кодом
или конфигурацией и проверяется автотестом (идентификаторы SEC-xx — в `tests/`).

## 1. Назначение и границы

Сервис принимает обезличенный снимок раздела 2 ЭНД, синхронно возвращает замечания детерминированных правил,
асинхронно — замечания локальной LLM, ведёт неизменяемый журнал и отвечает шлюзу отправки. Решение о допуске принимает
человек в HSE (шлюз `GET /v1/gate` — только вердикт). Публичного входа нет: сервис работает во внутренней сети.

## 2. Требования и их реализация

| № | Требование | Реализация | Тест |
| --- | --- | --- | --- |
| 1 | Журналы хранятся не менее 3 лет, в оперативном доступе не менее 2 месяцев | Журнал проверок — в БД, функций удаления нет; логи приложения — JSON в stdout → центральный сервер логов платформы (срок хранения: оперативно 2 месяца, архив 3 года) | SEC-01 |
| 2 | Журналы защищены от вмешательства | Триггеры запрещают `UPDATE`/`DELETE` в `check_run`, `run_event`, `finding`, `finding_action`, `kb_event`; роль `aicheck_app` не имеет этих прав; события ИБ пишутся независимо от `LOG_LEVEL` | SEC-02, SEC-03 |
| 3 | Идентификация, RBAC, MFA | JWT RS256 (`iss`, `aud`, `exp`, `sub` обязательны); роли `hse-backend`, `ai-admin`; для `ai-admin` обязателен `amr = mfa`; mTLS — уровень платформы | SEC-04 |
| 4 | Персональные данные в РК | Маскирование ИИН, телефонов и e-mail (`[ИИН]`, `[ТЕЛ]`, `[EMAIL]`) до записи и до вызова LLM; БД и LLM — на серверах в Республике Казахстан | SEC-05, SEC-06 |
| 5 | Прозрачность ИИ | У каждой находки LLM `source = ai`, `generated = true`; в ответе — модель и версия промпта; результаты ИИ — в журнале | SEC-07 |
| 6 | Защита от внедрения инструкций | Случайные ограничители, запрет инструкций из данных в системном промпте, схема ответа, верификатор (9 фильтров) | SEC-08 |
| 7 | Сетевая изоляция | Исходящие вызовы только на хосты `ALLOWED_OUTBOUND_HOSTS` (проверка при старте и перед каждым запросом); редиректы не выполняются | SEC-09 |
| 8 | Шифрование каналов | TLS 1.2+, проверка сертификатов всегда включена; собственной криптографии нет (HMAC — стандартная библиотека) | SEC-10 |
| 9 | Секреты | Только из файлов секретов; скраббер логов маскирует `Authorization`, `api_key`, `secret`, `token`; ключ не попадает в исключения и метрики | SEC-11 |
| 10 | Безопасная разработка | Зависимости с хешами (`requirements.lock`), `bandit`, `pip-audit`, SBOM (CycloneDX), образ non-root, read-only ФС, без компиляторов | SEC-12 |
| 11 | Контроль входных данных | `extra = forbid`, лимиты размера (тело 256 КБ, строка 2000 символов, ≤ 30 строк на пункт, ≤ 50 строк рисков), NFC, удаление HTML и управляющих символов, лимит длины входа для regex | SEC-13 |
| 12 | Документация | Этот документ | ревью при приёмке |
| 14 | Загрузка документов | Тип по сигнатуре (`%PDF`, ZIP-контейнер DOCX), ≤ 20 МБ, разбор в отдельном процессе с таймаутом 60 с, роль `ai-admin` с MFA, каждое изменение в `kb_event` | SEC-14 |
| 15 | Режим А | CORS только для адреса HSE, пользовательский токен проверяется по JWKS корпоративного IdP, чужой прогон — 404, лимит прогонов на пользователя | SEC-15 |

## 3. Матрица доступа

| Эндпоинт | `hse-backend` | пользователь (режим А) | `ai-admin` (MFA) | без токена |
| --- | --- | --- | --- | --- |
| `POST /v1/checks`, `GET /v1/checks/{id}`, `…/answers`, `POST /v1/findings/{id}/actions` | да | да, только свои прогоны | нет | 401 |
| `GET /v1/kb/clauses/{code}/{no}` | да | да | нет | 401 |
| `GET /v1/gate`, `POST /v1/sync`, `GET /v1/catalog/version` | да | нет (403) | нет | 401 |
| `POST /v1/admin/rulesets`, `…/activate`, `POST /v1/admin/catalog` | нет | нет | да | 401 |
| `/v1/admin/kb/*` | нет | нет | да | 401 |
| `/v1/health`, `/v1/ready`, `/metrics` | — | — | — | да (только внутренняя сеть) |

Администратор не имеет прав на изменение журнала: ни в API, ни в БД (роль приложения), ни в коде.

## 4. Перечень данных

| Данные | Где хранятся | Срок | Примечание |
| --- | --- | --- | --- |
| Снимок раздела 2 (тексты мероприятий, коды, ответы на вопросы) | `check_run.request` | не менее 3 лет (журнал) | после маскирования; ИИН, телефоны, e-mail заменены |
| Находки, действия пользователей | `finding`, `finding_action` | не менее 3 лет | в действиях — `user_ref` (непрозрачная ссылка) |
| Версии справочников и пакетов правил | `catalog_snapshot`, `ruleset` | пока нужны для перепроверки | |
| Нормативные документы | `kb_document`, `kb_clause` | по решению экспертов | |
| Кеш ответов LLM, очередь, исходящие callback | `llm_cache`, `job`, `callback_outbox` | кеш 30 дней (`purge-cache`) | служебные |
| Логи приложения | stdout → сервер логов | 2 месяца оперативно, 3 года архив | без текстов мероприятий, токенов и ключей |

ФИО в БД не хранятся: HSE подставляет роли вместо ФИО участников. **Допущение режима А:** фронт вызывает сервис напрямую,
поэтому ФИО, написанные пользователем внутри текста мероприятия, доходят до сервиса и локальной модели внутри
корпоративного контура; в логи тексты не попадают, ИИН, телефоны и e-mail маскируются.

## 5. Потоки данных

1. Фронт/HSE → сервис: HTTPS (TLS 1.2+), JWT. Сервис маскирует ПДн, проверяет и сохраняет снимок.
2. Сервис → БД PostgreSQL (на территории РК): TLS (`sslmode=verify-full`).
3. Воркер → локальная LLM (на территории РК): HTTPS, ключ из файла секрета, хост в `ALLOWED_OUTBOUND_HOSTS`.
4. Воркер → HSE: callback `POST` с подписью HMAC-SHA256 (`X-Timestamp`, `X-Signature`); при недоставке HSE забирает результат
   через `GET /v1/checks/{id}`.
5. Сервис → IdP (режим А): загрузка ключей JWKS, кеш 10 минут.
6. Сервис → HSE: экспорт справочников (`HSE_CATALOG_EXPORT_URL`).

Других исходящих вызовов нет; в интернет код не обращается.

## 6. Журналы и сроки

- Журнал проверок (`check_run`, `run_event`, `finding`, `finding_action`, `kb_event`) — только вставка, срок хранения
  не менее **3 лет**; удаление старше срока выполняется отдельной процедурой ИБ вне приложения (в коде удаления нет).
- Логи приложения — JSON в stdout; в центральном хранилище: оперативный доступ не менее **2 месяцев**, архив 3 года.
- События ИБ (`auth_denied`, `admin_action`) пишутся всегда, независимо от `LOG_LEVEL`.
- Команда `python -m aicheck.cli retention-report` показывает объём и возраст журнала для процедуры ИБ.

## 7. Резервное копирование

- БД: ежедневный логический дамп (`pg_dump -Fc`) и непрерывная архивация WAL платформой PostgreSQL; хранение копий — не менее
  срока хранения журнала; копии шифруются и хранятся на территории РК.
- Проверка восстановления — раз в квартал на тестовом стенде: восстановление, `alembic upgrade head`, `make golden`.
- Секреты резервируются средствами платформы секретов, не вместе с БД.
- Пакеты правил и справочники версионируются в БД; откат пакета правил — активация предыдущей версии
  (`POST /v1/admin/rulesets/{id}/activate`).

## 8. Реагирование на инциденты

1. Обнаружение: оповещения по метрикам (`auth_denied_total`, 5xx > 2 %, `callback_undelivered_total`), события ИБ в логах.
2. Компрометация ключа LLM или сервисного ключа: отозвать секрет в платформе, выпустить новый, перезапустить сервис;
   журнал `auth_denied`/`admin_action` покажет период использования.
3. Подозрение на утечку ПДн: остановить прием запросов (отозвать сервисный токен), оценить объём по `check_run`,
   уведомить службу ИБ ОМГ в сроки, установленные внутренним регламентом.
4. Нарушение целостности журнала: попытка `UPDATE`/`DELETE` приводит к ошибке БД и записи в журнале БД; расследование —
   по логам PostgreSQL и WAL.
5. Уязвимость в зависимости: `make sec` (`pip-audit`) падает; обновление через `make lock`, повторный прогон `scripts/ci.sh`.
6. После инцидента — запись в журнал инцидентов ИБ, корректировка этого документа.

## 9. Требования к развёртыванию

- БД и локальная LLM размещаются на серверах на территории Республики Казахстан (Закон № 94-V, ст. 12).
- Сетевые политики: сервис принимает вызовы только от HSE (и фронта в режиме А); исходящие — только к БД, LLM, HSE, IdP.
- Контейнер: non-root, read-only ФС (`/tmp` — tmpfs), `cap_drop: ALL`, `no-new-privileges`.
- СКЗИ, если их требует ТД ИБ ОМГ, подключаются на уровне платформы (mTLS, шифрование дисков и бэкапов).

## 10. Проверки качества и ИБ

`make lint typecheck sec` и `make test-stage N=7`: `ruff`, `mypy`, `bandit` (находки уровня medium и выше — отказ),
`pip-audit --strict`, `scripts/check_code.py` (запрет `verify=False`, `eval`, `exec`, `pickle`, `async def`, запрещённых
библиотек и секретов в исходниках; лимиты размера функций и модулей). SBOM: `make sbom` → `reports/sbom.cdx.json`.
